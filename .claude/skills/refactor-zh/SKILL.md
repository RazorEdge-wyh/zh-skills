# 中文工程规范 · 安全重构（refactor-zh）

当用户要求重构、清理、优化代码结构时激活本技能。重构**不是重写**，铁律是：**行为不变、小步提交、可随时回滚**。

## 重构纪律

1. **先有测试再动手**：没有测试时，先补"行为快照"（关键路径的最小测试）或用 `git stash` 兜底。
2. **一次只做一个意图**：命名规范化、函数拆分、去重复，别混在一次改动里。
3. **每次小步提交**：一个重构动作一个 commit（见 commit-zh），commit message 写明"纯重构：无行为变化"。
4. **每步可验证**：重构后跑测试、能编译、能启动。不满足就回退。
5. **性能与可读性冲突时**，先可读性；量化到真实瓶颈时再优化。

## 重构动作清单（按优先级）

### 1. 命名规范化（最高性价比）
- 拼音 → 英文：`jine` → `amount`，`shijian` → `createdAt`，`mingcheng` → `name`。
- 语义不明 → 明确：`data` → `orderList`，`flag` → `isPaid`。
- 统一风格：方法动词开头、常量大写、类名 PascalCase。
- 全局搜索确认改动范围，防止漏改（改一半更危险）。

### 2. 注释优化
- 删除"是什么"注释（`// 遍历`）、废弃注释、调试残留。
- 补上缺失的"为什么"注释：业务取舍、特殊边界、性能考量的原因。
- 把过时注释**更新为真实行为**，不要留着和代码矛盾的注释。

### 3. 函数拆分
- 拆分条件：>50 行、参数 >4、嵌套 >3、一个函数做多件事。
- 提取时用"命名即文档"：新函数名 = 旧代码块的意图。
- 早退（guard clause）替代深嵌套：`if (!user) return;` 而不是 `if (user) { ... }`。

### 4. 消除重复
- 相同逻辑 → 抽公共函数/工具；相似逻辑 → 抽象差异点参数化。
- 重复的常量、魔数 → 常量或枚举。
- 复制粘贴的 UI 片段 → 公共组件。

### 5. 死代码清理
- 未被引用的导出、`console.log` 残留、注释掉的代码块 → 删除。
- 删除前全局搜索确认无引用；拿不准的先问或保留标注。

### 6. 结构整理
- 相关代码聚合：同一模块的辅助函数就近放置。
- 依赖方向清晰：工具层不反向依赖业务层。
- 明显的层级错位（业务逻辑混进工具函数）移动到正确位置。

## 输出约定

- 重构前：列出**计划清单**，标注每项的影响范围，让用户确认再动手。
- 重构后：给出**变更摘要**，说明动了什么、行为如何保证不变、跑了哪些验证。
- 涉及公共 API / 外部依赖签名的改动，必须高亮提醒（可能影响调用方）。

## 完成标准

- [ ] 所有测试通过（或至少关键路径验证通过）
- [ ] 无拼音命名残留（`git grep` 复查）
- [ ] 注释与代码一致，无翻译腔
- [ ] 每个重构动作独立 commit
- [ ] 能构建、能启动
